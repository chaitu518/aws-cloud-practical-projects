## Logs

Logs are records of events or activities generated by a system.
In this project, VPC Flow Logs are records of network traffic going to and from your VPC network interfaces. They help you monitor, troubleshoot, and analyze network traffic.

Log groups are containers in CloudWatch that organize and store related log streams.
In this project, the VPC Flow Logs are stored in a CloudWatch Log Group, where I can view and analyze the network traffic records.

## IAM Policy and Roles

I created an IAM policy because VPC Flow Logs need permission to create log groups and streams and write log events to CloudWatch. This policy grants the required CloudWatch Logs permissions so the network traffic records can be stored and analyzed.

I also created an IAM role because the VPC Flow Logs service needs an identity to use the permissions defined in the IAM policy. We attach the policy to the role, and VPC Flow Logs can then assume that role to write network traffic logs to CloudWatch.

A custom trust policy defines who or which AWS service is allowed to assume and use an IAM role.

## Connectivity troubleshooting

My first ping test between my EC2 instances had no replies, which means the instances were not able to communicate with each other, indicating that there was a network connectivity issue that needed to be troubleshooted.

![Image](http://nextwork.ai/sparkling_purple_peaceful_chinese_gooseberry/uploads/aws-networks-monitoring_99d4ba42)

I could receive ping replies when I used the other instance's public IP address, which means the traffic was going through the public internet path via the Internet Gateway, rather than communicating directly between the two VPCs through the VPC peering connection.

---

## Connectivity troubleshooting

Looking at VPC 1's route table, I identified that the ping test using Instance 2's private IP address failed because there was no route to VPC 2 through the VPC peering connection. The peering connection had not yet been configured in the route table.

### To solve this, I set up a peering connection between my VPCs

I also updated both VPCs' route tables so that each VPC knows where to send traffic destined for the other VPC through the VPC peering connection.

## Analyzing flow logs

Flow logs tell us about the network traffic flowing to and from resources in a VPC, including the source and destination IP addresses, ports, protocols, traffic direction, and whether the traffic was accepted or rejected.

For example, the flow log I've captured tells us that traffic from 10.0.10.138 to 10.1.13.126 using the ICMP protocol was accepted. It also shows the network interface involved, the amount of traffic transferred, and the start and end timestamps of the connection.

## Logs Insights

CloudWatch Logs Insights is a tool used to search, filter, and analyze log data stored in CloudWatch.
In this project, I use it to query VPC Flow Logs and identify specific network traffic, such as accepted or rejected connections between my EC2 instances.

SOURCE "arn:aws:logs:ap-south-2:226123186796:log-group:nextwork-vpcflow-logs-group" START=-1d END=0s |
stats sum(bytes) as bytesTransferred by srcAddr, dstAddr
| sort bytesTransferred desc
| limit 10
I ran this query in CloudWatch Logs Insights. This query analyzes the VPC Flow Logs to calculate the total number of bytes transferred between each source and destination IP address, sort the results by the highest traffic volume, and display the top 10 connections.
